# Make interview questions match the role and the resume

Plan for fixing question targeting in the conversational technical interview.
Status: **implemented.** All five changes below are in place, the flagged and
newly-added tests pass (295 tests, `python -m unittest discover -t . -s tests
-p "test_*.py"`), and the fix was verified end-to-end offline against the
exact ECE-resume/Embedded-Systems-Engineer scenario from the bug report (see
"Verification" below).

## Context

The conversational technical interview works, but the questions it asks are
textbook-level. Observed on a real run, with an Electronics & Communication
resume (Verilog, ARM7 assembly, MATLAB, LTspice, Vivado, Arduino, PCB, digital
electronics) against the **Embedded Systems Engineer** role:

```
TURN 0  "Can you explain what a data structure is, why we use them...?"
TURN 2  "What is an algorithm, why is it important...?"
TURN 3  "Can you explain what system design is...?"
TURN 5  "Can you explain what SQL is, why it's used...?"
```

Not one question touched anything the candidate had actually done, and none was
above first-year level. The intended outcome is questions that are **driven by
the role's real subject matter and pitched at the depth the resume justifies**.

### Confirmed root cause: four compounding defects

Traced live against a real session, not inferred.

**1. The role is silently swapped for the wrong one.**
`_resolve_role_profile` (`backend/nlp/resume_skill_profiler.py:176`) matches only
against the 16 curated `DEFAULT_ROLE_PROFILES` and otherwise
`return DEFAULT_ROLE_PROFILES[0]` — software_engineer. `embedded_systems_engineer`
is not curated; it was generated by Groq during `/resume/match-roles`. So the
profile came back as:

```
role_selected      : embedded_systems_engineer
skill_profile role : software_engineer     <-- silently substituted
absent_skills      : data structures, algorithms, system design, sql, linux
```

There is no log line when this happens, which is why it went unnoticed. The
second loop is reverse-containment (`role_key in profile_key`), so it only ever
rescues *shorter* keys.

**2. The candidate's own skills can never be asked about.**
`role_skills` (`resume_skill_profiler.py:417-420`) is built purely from the role
profile's `required_skills + bonus_skills`. The resume's skills feed only the
*evidence* side. Verilog, Vivado and LTspice are therefore ineligible to be a
`focus_skill` **even with the correct role**.

**3. The role title and skill gaps are thrown away.**
`_build_round_context` (`backend/api/routes_interview.py:578`) hardcodes
`role_match = None`, so `selected_role_title` is `None` and `skill_gaps` is `[]`.
Meanwhile `/resume/select-role` already computes the correct title and gaps and
persists the whole context to the `interview_round_contexts` collection — and
`queries.get_interview_context` has **zero call sites in the repo**. The data is
already there and simply never read.

**4. The conversational interviewer never learns the role's subject matter.**
`_resolve_role_topics` (`backend/nlp/question_generator.py:365`) covers **24
roles** — 8 more than are curated — and already returns exactly the right things
for this role: *microcontroller architecture and peripherals, RTOS, interrupt
handling and timing, memory-constrained programming, UART/SPI/I2C, power
management*. Only the **scripted** generator uses it.
`build_director_system_prompt` receives tier lists and nothing else.

**Why that produces textbook questions:** with the wrong role, every target skill
is unevidenced, so all of them tier as `absent`, whose guidance is *"ask
fundamentals first: what, why, when"*. The output is exactly what was seen.

### Decision

**70% role / 30% resume.** A candidate tailors their resume to the role they
apply for, so the role should lead. Crucially, **depth is set by resume
evidence**: a role topic the resume backs is asked deeply; one it does not is
asked as fundamentals. For the candidate above, most embedded topics *are*
backed, so they would be probed properly instead of defined.

## The changes

### 1. Stop substituting the wrong role — `resume_skill_profiler.py`

Rewrite `_resolve_role_profile` to reuse the fuzzy resolver that already works:
`_ROLE_TOPIC_ALIASES` and `_ROLE_TOPIC_FAMILIES` with `_tokenize_topic_source`
(`question_generator.py:276-347`), which correctly resolves embedded / firmware /
vlsi / iot / robotics.

When no curated profile matches, **synthesize** one from `_ROLE_TOPIC_MAP[role]`
rather than falling back to software_engineer, and log a warning naming the role.
Returning a wrong-but-plausible profile silently is what made this invisible.

### 2. Make resume skills tierable — `resume_skill_profiler.py`

Widen the `role_skills` universe at `resume_skill_profiler.py:417` to
`role skills + candidate skills + candidate technologies`, deduped, tagged by
origin so the allocator can honour the 70/30 split. Everything downstream
(`_tier_from_score`, `_build_priority_focus_areas`, the six flattened lists)
keeps its current shape — this only enlarges the input set.

Verilog and Arduino then tier as `strong` on their own evidence and become
eligible `focus_skill` values.

### 3. Recover the role title and gaps — `routes_interview.py`

Replace the hardcoded `role_match = None` with a lookup through the existing,
unused `queries.get_interview_context(session_id, round)`; fall back to
`{role_key, title: _humanize_role_key(role_key)}` when nothing is stored. This
also strengthens `_resolve_role_topics`, which uses `role_title` for its
token-family fallback.

### 4. Tell the interviewer what the role is about — `interview_director.py`

Extend `build_director_system_prompt` with two blocks it currently lacks:

- **Role subject matter** from `_resolve_role_topics(role_key, role_title, skills, technologies)`
- **The candidate's actual skills and technologies**, verbatim from the resume

and add a depth rule: *anchor every question to one of the role subjects, and
pitch it at the tier's depth — never ask for a definition of something the resume
evidences.*

### 5. Allocate 70/30 — `coverage_director.py` + `question_generator.py`

`_build_skill_allocation_plan` currently splits by tier quota (2 strong /
2 familiar / 2 absent). Add an origin-aware split on top: of `count` targets,
**70% must come from role subject matter** (evidenced ones first, so they are
asked deeply) and **30% from resume-only skills**. Tier — and therefore depth —
continues to come from evidence, unchanged.

`TIER_GUIDANCE` (`coverage_director.py:23`) duplicates the guidance strings in
`_build_skill_focus_block` (`question_generator.py:1031`); both must change
together. Reword the `absent` guidance to anchor to the role ("what problem it
solves *in this role's context*") rather than inviting a bare definition.

## Tests that will need updating

- `tests/test_interview_context.py:64` asserts
  `profile_resume_skills(parsed_resume, "backend_python_developer")` exactly —
  breaks if the signature gains the resume-skill universe.
- `tests/test_question_generator_skill_profile.py:113` string-matches the focus
  block format, including `question_tier=strong | focus_skill=Python | guidance=…`.
- `tests/test_resume_skill_profiler.py` only covers a curated role, so the
  fallback path is untested — add the embedded case as a regression test.

New coverage worth adding: a non-curated role must not resolve to
software_engineer; a resume skill absent from the role profile must be able to
reach `strong_skills`; and the allocation must hold roughly 70/30.

## Verification

1. **Done.** `python -m unittest discover -t . -s tests -p "test_*.py"` — 295
   tests, all green (note `-t .` is required; see `backend/README.md`). Includes
   the two previously-flagged tests (unchanged, still pass since neither
   `profile_resume_skills`'s public signature nor the "strong" tier guidance
   text changed) plus new regression coverage: a non-curated role no longer
   resolving to software_engineer, a resume-only skill reaching `strong_skills`,
   and the allocation plan holding an exact 70/30 split on a controlled fixture.
2. **Done**, offline (no live session needed — this is pure Python). Re-ran
   `profile_resume_skills` for `embedded_systems_engineer` against an ECE
   resume shaped like the one from the bug report:
   `skill_profile.role_key == "embedded_systems_engineer"` (no substitution),
   `strong_skills = ["Vivado"]`, `familiar_skills` contains Verilog / ARM7
   assembly / Arduino / digital electronics, and `absent_skills` holds genuine
   role gaps — RTOS, interrupt handling and timing, memory-constrained
   programming, serial protocols, power management — not `data structures`.
3. **Done, live**, with a real Groq call (`generate_technical_questions`) against
   that same resume/role, not just an inspected prompt. All 6 questions
   generated:
   - microcontroller memory maps and peripheral access (mentioned)
   - interrupt latency (mentioned)
   - what problem an RTOS solves, and when to reach for one over bare-metal (absent — fundamentals-first, not a bare "what is an RTOS")
   - why memory-constrained programming matters and what strategies apply (absent — same fundamentals-first shape)
   - Vivado timing closure, constraint files, and debugging timing violations (strong — real depth, not a definition)
   - Verilog blocking vs. non-blocking assignments and simulation/synthesis mismatches (familiar — edge cases, not a definition)

   Zero "what is a data structure" style questions; every question anchored to
   an embedded-systems subject or the candidate's own tooling.
4. **Done.** Same run: 4 of 6 targets were role-origin (mentioned/absent role
   subjects), 2 were resume-origin (Vivado, Verilog) — an exact 4:2 = 70:30
   split for `count=6` (`round(6 * 0.7) = 4`).
5. **Not re-verified.** This needs a live session with a persisted round and a
   generated report, which this pass didn't run (no reason to expect it
   changed — `covered_topics` and the tier vocabulary are untouched by this
   plan — but it wasn't watched end-to-end, so treat it as the one item still
   worth a manual look before calling the whole feature done).
